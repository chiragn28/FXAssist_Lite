# observability

Metrics, dashboards, alerts and traces (ADR-012, Phase 3).

```
gateway --(OTel SDK)--> :9464/metrics --(scrape every 5 s)--> Prometheus --> Grafana
   |                      (compose network only, OBS-04)          |
   |                                                          alert rules
   +--(OTel spans, optional)--> Langfuse Cloud or any OTLP/HTTP endpoint (DEP-03: bounded, 2 s)
```

| What | Where |
|---|---|
| Grafana | http://127.0.0.1:3000 (dashboard "FXAssist gateway"; viewable without login, admin password in `.env`) |
| Prometheus | http://127.0.0.1:9090 (targets: `/targets`, alerts: `/alerts`) |
| Scrape config | `prometheus/prometheus.yml` (gateway, Qdrant, Prometheus itself) |
| Alert rules | `prometheus/rules/fxassist.yml`; each names its runbook in `docs/runbooks/` |
| Dashboard | `grafana/dashboards/fxassist.json`, generated by `grafana/build_dashboard.py` (`make dashboard`). Edit the spec, not the JSON; a test fails if they differ |

Start it with `make up` (with Ollama) or `make up-mock` (mock LLM, no model download), then `make load` to see the panels move.

## Traces

Set `FXA_LANGFUSE_PUBLIC_KEY` and `FXA_LANGFUSE_SECRET_KEY` in `.env` (free Hobby tier, no card), or `FXA_OTLP_TRACES_ENDPOINT` for any OTLP/HTTP backend. One trace per request: FastAPI's server span, `fxassist.ask` (outcome, cache, coalescing), `agent.<node>` for each graph step, and `llm.chat` per model call with `gen_ai.*` attributes (model, tokens). The adapter sends a W3C `traceparent` header, so a model server that traces (vLLM can) joins the same trace. Question and answer text are attached only with `FXA_TRACE_CONTENT=true`, truncated to 1000 characters and with API keys redacted (OBS-02).

## Panels

Each panel's description is also its (i) tooltip in Grafana, and each says what "No data" means (OBS-03). Generated by `python observability/grafana/build_dashboard.py --markdown`:

| Panel | Query | What it means |
|---|---|---|
| Requests per second by outcome | `sum by (outcome) (rate(fxa_requests_total{route="/v1/ask"}[1m]))` | How many /v1/ask requests finish each second, split by what happened: answered, abstained (not enough information), out_of_scope, clarify, declined_advice, refused, error, or none (rejected before the agent ran, e.g. 401/429/422). |
| Errors per second by code | `sum by (code) (rate(fxa_errors_total[1m]))` | Failures by error code: llm_timeout, llm_unavailable, llm_circuit_open, store_unavailable, rate_limited, unauthorized and so on. Each code maps to one HTTP status (services/gateway/README.md). |
| Fallback rate | `sum(rate(fxa_requests_total{outcome=~"abstained\|out_of_scope"}[5m])) / sum(rate(fxa_requests_total{outcome!="none"}[5m]))` | Share of requests the agent did not answer from the documents: abstained (nothing relevant enough) plus out_of_scope. A sudden rise usually means retrieval broke (empty or wrong collection) rather than users asking odd things. |
| Cache hit ratio | `sum(rate(fxa_cache_lookups_total{result="hit"}[5m])) / sum(rate(fxa_cache_lookups_total{result=~"hit\|miss\|skip"}[5m]))` | Share of cache lookups that found an answer. Lookups skipped because Redis is down are counted in the denominator, so an outage shows up as a drop here. |
| Request latency p50 / p95 (fresh answers) | `histogram_quantile(0.5, sum by (le) (rate(fxa_request_duration_seconds_bucket{cached="false",outcome="answered"}[5m])))`<br>`histogram_quantile(0.95, sum by (le) (rate(fxa_request_duration_seconds_bucket{cached="false",outcome="answered"}[5m])))` | Whole request time for answers computed now (cache misses), from the gateway receiving the request to the answer being ready. Cached answers are excluded: they take milliseconds and would hide the real latency. |
| Stage latency p95: queue, retrieval, time to first token, LLM total | `histogram_quantile(0.95, sum by (le, stage) (rate(fxa_stage_duration_seconds_bucket[5m])))` | Where the time goes. queue: waiting for a free agent slot. retrieval: embedding the question and searching Qdrant. ttft: from sending the answer request to the model's first token (excludes queue and retrieval). llm: all model calls of the request together, including the grader. |
| Generation speed (tokens per second, p50) | `histogram_quantile(0.5, sum by (le) (rate(fxa_llm_tokens_per_second_bucket[5m])))` | Decode speed of answer generation: tokens after the first, divided by the time after the first token. Needs a model server that reports token usage (Ollama and vLLM do; the mock does in its 'ollama' format). |
| Tokens generated per second (all calls) | `sum by (kind) (rate(fxa_llm_output_tokens_total[1m]))` | Total model output rate across all requests, by call kind: text (answers, rewrites) and json (grader). |
| LLM calls by result | `sum by (kind, result) (rate(fxa_llm_calls_total[1m]))` | Model calls per second by kind and result: ok, or the error code (llm_timeout, llm_unavailable, llm_empty, llm_bad_response, cancelled...). |
| Model call failure ratio | `sum(rate(fxa_llm_calls_total{result!="ok"}[2m])) / sum(rate(fxa_llm_calls_total[2m]))` | Share of model calls that did not succeed: timeouts, server errors, broken streams, or refused by the open circuit breaker. This is the signal that caught a dead model in the drill; request error rates did not, because the cache and the breaker hide it (docs/runbooks/llm-timeout-storm.md). |
| Circuit breaker state | `max(fxa_llm_circuit_state)` | 0 = closed (normal), 1 = half-open (one trial call allowed), 2 = open (model calls paused after repeated failures; requests get 503 quickly). |
| Agent runs in progress | `sum(fxa_agent_runs_active)` | Agent runs executing in worker threads right now (at most FXA_MAX_CONCURRENT_RUNS). At the limit, new requests queue; past the queue timeout they get 503 busy. |
| Context truncations and coalesced requests | `sum(rate(fxa_context_truncations_total[5m]))`<br>`sum(rate(fxa_coalesced_requests_total[5m]))` | truncations: excerpts dropped or cut to fit the model's context window (RET-06). coalesced: requests that waited for an identical request's answer instead of starting their own run (API-04). |
| Dependency failures and degraded modes | `sum by (dependency) (rate(fxa_dependency_failures_total[5m]))`<br>`sum(rate(fxa_rate_limit_decisions_total{backend="memory"}[5m]))`<br>`sum(rate(fxa_request_log_dropped_total[5m]))` | Failures talking to Redis, PostgreSQL or Qdrant; rate-limit decisions made by the in-memory fallback (Redis down); request-log entries dropped (PostgreSQL down too long). All should be zero in normal operation. |
